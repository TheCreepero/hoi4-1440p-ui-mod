# HOI4 1440p UI Mod - Development & Agent Rules

## 1. Mod Architecture & Workspace Layout
- **Mod Role**: High-resolution UI mod that redesigns Hearts of Iron IV screens for 1440p (`2560x1440`) and higher displays: larger and regrouped panels, a place of its own for every value a screen already has, larger text, and hotkeys for existing buttons. Since phase D2 it also adds "manager" pages of its own beside the vanilla panels (scripted GUIs, Milestone D of `wiki/Roadmap.md`), and since version 1.6 a Records window that keeps a record of the campaign for role-play (Milestone E, `wiki/Roleplay-Pages.md`).
- **Checksum**: The reworked screens live in `interface/` (`.gui`, `.gfx`) and `gfx/` (textures), which are outside the gameplay checksum. The manager pages are scripted GUIs and need script: four folders under `common/` (`scripted_guis`, `scripted_effects`, `on_actions`, `synchronized_dynamic_tokens`), every file named `mod1440_*`, plus `localisation/`. These change the checksum: the mod no longer works with Ironman and achievements, and in multiplayer every player needs it (user decision, 2026-10-12). Nothing else goes under `common/`, and `events/`, `history/` and `map/` stay empty; `tests/GuiInvariants.Tests.ps1` and `tests/ScriptedGuis.Tests.ps1` hold the line.
- **Phased Work**: The mod is built one screen per phase. Before starting or continuing a phase, read `wiki/Roadmap.md` (phase list, status), `wiki/Design-Rules.md` (the rules and the per-screen recipe), `wiki/Engine-Facts.md` (what is confirmed, provisional or untested about the engine) and the phase's notes in `wiki/phases/` (template: `wiki/Phase-Template.md`).
- This project follows a unified single-root mod layout:
  - **Workspace & Git root**: `C:\dev\hoi4-1440p-ui-mod` (Git repository root containing `.git/`)
  - All mod descriptors (`descriptor.mod`), build tools (`build.ps1`), interface definitions (`interface/`), content (`common/`), tests (`tests/`), and agent configurations (`GEMINI.md`) reside at the project root.
  - `tools/` (inspection, render and harness scripts), `baseline/` (vanilla reference copies of overridden windows), `reference/` (captures of every screen, vanilla and reworked) and `scratch/` (renders, captures, caches; git-ignored) are dev-only and excluded from packages.

## 2. Clausewitz GUI & File Format Invariants
- **UTF-8 Without BOM**: All Clausewitz script and interface files (`.mod`, `.txt`, `.gui`, `.gfx`) must be saved in UTF-8 without BOM. Never use standard Windows PowerShell `Set-Content -Encoding UTF8` because it writes a BOM (`\ufeff`). Always write text files using:
  `[System.IO.File]::WriteAllText($path, $content, [System.Text.UTF8Encoding]::new($false))`
- **Hardcoded C++ Widget Bindings**: The engine binds gameplay data to widgets by `name = "..."`. Never rename a vanilla widget or change its element type inside an overridden window. A vanilla widget may move into a container of the mod's own, named `mod1440_*`, because `hoi4.exe` on this machine is patched to search nested containers (`wiki/Engine-Facts.md` W34); scrollbars, list boxes and browsers stay under their vanilla parent. After a game update run the Modding Manager's `Scripts\Executable\Set-HoiRecursiveLookups.ps1 -Status` and patch again before a game check, or wrapped widgets stay empty.
- **No New Data Or Actions**: The engine fills only the widgets its code asks for, so a redesign can re-arrange, enlarge, caption and add hotkeys, but cannot add live values or working buttons. Before proposing an addition, look the window up in the Modding Manager's `Artifacts/executable/window-bindings-1440p*.md` and read "What a redesign can add" in `wiki/Design-Rules.md`. Scripted GUIs can add both, for values of the own country: they are the manager pages of Milestone D and follow section 2a.
- **One Override File Per Screen**: Put a screen's reworked top-level windows in `interface/zz_1440p_<screen>.gui` and leave the vanilla file alone. The game uses the last loaded definition of a window name and loads `.gui` files in name order, so the `zz_` prefix is what makes the override win.
- **Baseline Before Rework**: Start or extend a screen file with `tools/New-OverrideFile.ps1 <screen> <file.gui> <window> [<window> ...]`. It saves each window's vanilla text under `baseline/`, writes untouched copies into `interface/zz_1440p_<screen>.gui` and creates `tools/scenes/<screen>.json`. The test suite fails for an overridden window without a baseline, and for any named vanilla widget that is missing or moved.
- **Links Live In Code**: Which rows fill a list or grid, and which file-level `@variables` a window needs, is known only to the game code. Record each in `tools/gui-links.json`; the tests, the renderer and the harness read it.
- **Review Against The Baseline**: After editing, run `tools/Compare-Baseline.ps1 zz_1440p_<screen>.gui` (`-Group` for one line per widget) and read every changed value. Nothing but intended changes may appear.
- **Sprite Naming**: Name new sprites `GFX_1440p_*` and declare them in `interface/1440p_ui.gfx`. Leave vanilla sprite names untouched.
- **Art From Vanilla Assets**: Build every image from vanilla game assets, following the order of options in `wiki/Design-Rules.md`. AI-generated images are not allowed anywhere in the mod.
- **Key-Value Syntax**: `descriptor.mod` must strictly follow `key="value"` without spaces around the `=` operator.
- **Bracket Balance**: Curly braces `{}` and double quotes `""` must always be strictly balanced.
- **Usable Slot Width & Scroll Math**: In scrollable windows with `verticalScrollbar = "right_vertical_slider"`, match `slotsize.width` to the entry `containerWindowType.width`, and set `scroll_wheel_factor` to an integer multiple of `slotsize.height`.
- **Vanilla Lookups**: Inspect vanilla `.gui` structure with `tools/Show-GuiOutline.ps1 <file.gui> [<window>] [-All|-Comments]` instead of guessing (`-Comments` lists the sizes "set in code"). For `.gui`/`.gfx` syntax and element templates, use the user-level `hoi4-gui-modding` skill. For other vanilla facts, use the user-level `hoi4-vanilla-lookup` skill.
- **Reading The Executable**: the Modding Manager keeps a Ghidra project of `hoi4.exe` and the tools around it in its `Scripts\Executable` folder, whose `README.md` is the runbook. When a question is what the code fills, sets or binds, read it there before promising a layout or asking for a game check; the open questions are Milestone F in `wiki/Roadmap.md`. Never change `hoi4.exe` on your own: a patch is the user's decision, goes through the Manager's scripts so its hashes are recorded, and makes the mod local-only (`wiki/Roadmap.md`, Decisions). The installed executable carries the division icon picker patch [LIM-003]. It changes only that picker, which this mod does not touch, so game checks still show this mod as the unpatched game shows it.

## 2a. Scripted GUIs (Manager Pages)
- **Read First**: `wiki/Scripted-GUIs.md` (the rules and the catalogue of pages), `wiki/Roleplay-Pages.md` (the planned pages of Milestone E that keep a record of the campaign, with a plan each under `wiki/phases/E*.md`), `wiki/Script-Reference.md` (the script language, with how sure each fact is) and rows X1 to X73 of `wiki/Engine-Facts.md`. Look a command up in the game's `documentation/` folder or with the `hoi4-vanilla-lookup` skill before writing it, never from memory.
- **Generated Files**: `python -I tools/build_managers.py` writes every file of the manager pages and of the Records window: `interface/mod1440_*.gui`, `common/**/mod1440_*.txt` and `localisation/*/mod1440_l_*.yml`. The Records window is in `tools/build_records.py`, which the tool imports, and the game's medals in `tools/unit_medals_table.py`. Change the tools, not their output; the tests fail when the output is stale.
- **Tables Of Game Content**: script cannot ask the game for a character's portrait or for the victory points, so the mod carries two lists made from the installed game: `tools/portraits_table.py` and `tools/victory_points_table.py`. `python -I tools/make_game_tables.py` writes them; run it after a game update, then the build tool. A test compares them with the game. With `--mods` it writes two more from the mods of the launcher's playset: `tools/portraits_mods_table.py`, the portraits of the officers those mods add, and `tools/victory_points_mods_table.py`, the victory points of a playset whose states are not the game's (Road to 56). The build uses them when they are there. A name the loaded game does not know is not found and logs nothing (X68), and script takes the table of the map whose number of states the loaded game has (X72). The strips of medal pictures are sprites of this mod on the game's pictures (`GFX_1440p_medal_<set>`, `python -I tools/list_medals.py --sprites`), because another mod's `interface/medals.gfx` drops the game's (L10).
- **Officers Are Kept Through `mod1440_of_me`**: a general whose command came by an effect (how the game's focuses and most mods add them) has no number: `THIS` and the game's arrays `army_leaders` and `navy_leaders` hold nothing for him (X66). Reach officers with `every_army_leader` and `every_navy_leader`, and store one with `mod1440_of_me = yes` and the temporary variable `of_me`, never with `THIS`. A place kept for a character goes stale when the game's list of characters changes; `mod1440_of_refs` finds that out and puts the lists right, so a new list that holds a person's place is added to `mod1440_ch_remap` (`tools/build_records.py`, `places()`).
- **Show, Navigate And Keep Records**: a scripted button changes its page (fold, sort, filter) or moves the camera. The mod may also write records: its own variables, arrays and flags (`mod1440_*`) on a country, a state or a character, and lines the game keeps for show, such as an entry in a division's history. A record is written on the player's click or by a hook the player can switch off. Not allowed: giving the player what the game charges for (a unit, a building, equipment, a skill level, a trait, a medal's bonus without its price). The user loosened this on 2026-10-12 from "never change the game" for the role-play pages (`wiki/Roleplay-Pages.md`). `tests/ScriptedGuis.Tests.ps1` holds the list of commands the mod's script may use; a new command is added there first, and one that writes to the game with the page that needs it.
- **Own Country Only**: every scripted GUI is `player_context` and shows values of the player's country. Nothing about another country that the game's intelligence system would hide.
- **Localisation Has A BOM**: `.yml` files under `localisation/` are UTF-8 **with** BOM, the opposite of every other text file of the mod. The tool writes it.
- **Names After `@` Are Listed**: a name such as `infantry_equipment` in `num_equipment@infantry_equipment` goes into `common/synchronized_dynamic_tokens/mod1440_tokens.txt` (the tool does it), or the game logs an error each time the text is worked out.
- **Docking Needs `clipping = no`**: a page attached to a tab (`parent_window_token`) is cut off at the tab's window. It shows beside the panel only when that window, in the mod's override file, has `clipping = no`.
- **Live Rework**: a running game re-reads the script, the localisation and the container's `.gui` file a few seconds after a file under `common/scripted_guis/` changes (the tool gives one a new time stamp), and writes "Reloading Database" and any parse error to `error.log`. So a page is reworked in a game left open with `tools/Invoke-GameSteps.ps1 -Start`. New sprites (`.gfx`) and vanilla windows still need a restart, and so does a new text key that script holds as a token (X70).
- **Every Value Is Checked**: a value a page shows is compared with the game's own number in a game check before the page ships, and the comparison is logged in the phase notes. Names mislead: `num_armies` counts divisions.
- **Check Effects**: `python -I tools/check_effects.py` writes throwaway effects for a game left open: events while paused, the mod's daily round, a game as an earlier build or another set of mods left it, made-up months for History, officers without a number. Run one from the console with `effect mod1440_chk_<name>` and read `game.log`; `--restore` removes the file, and the tests fail while it is there. Keep an effect that proved useful in that tool, not under `scratch/`, which is not in the repository.

## 3. Seeing The Result
- **Render Before Asking**: `python -I tools/render_gui.py --scene <screen>` draws the screen from the override file with the real textures and fonts into `scratch/previews/` (`--over` composes it on the vanilla screenshot, `--bounds` outlines every widget, `--expand <dropdown>` opens one). Read the crop PNG with the Read tool. No game check is requested before the render has been looked at and the problems it shows are fixed. The scene file `tools/scenes/<screen>.json` holds the window positions, sample texts, rows per list and the widgets the code hides; keep it current.
- **Check In The Game Yourself**: the game re-reads no `.gui`, `.gfx` or texture file while it runs (`reloadinterface`, `reload <file>` and `reload_textures` report success and change nothing; `wiki/Engine-Facts.md` H3, H4), so every change is checked from a fresh start. `tools/Invoke-GameCheck.ps1 <screen> [<screen> ...]` does the whole round without a human in about two minutes: only-this-mod playset, `hoi4.exe -debug`, the menu clicks into a new 1936 game as Germany (paused, never saved), the scene's `setup` steps that bring the screen up, a capture and a 2x crop per scene into `scratch/checks/`, the `error.log` diff against `baseline/error.log.vanilla`, then it stops the game and restores the playset. Read the crops with the Read tool. `-Vanilla` captures the same screens without the mod, `-SaveReference` stores the captures for good under `reference/`, `-KeepRunning` leaves the game open for the user, `-NoRestart` reuses a running game. It takes over the main screen and the mouse while it runs, so ask the user for permission before starting the game, each time, saying what the launch is for, and batch changes: render first, launch when the render looks right.
- **Ten Days At Most, Never Save**: a check saves nothing, and stays paused on 1 January 1936 unless time is what it checks. The user's autosave is monthly: a check that let a month pass would overwrite the autosave of their own campaign. Since 2026-10-12 the user allows a check to run up to ten days inside January 1936, with a copy of `autosave.hoi4` made first and its hash compared afterwards (`wiki/Scripted-GUIs.md`, "Working on a page"; nine days left the file untouched, `wiki/Engine-Facts.md` X54). Read the clock from a capture after every burst. What needs more time than that, or a save, is asked of the user.
- **Other Mods Change What A Page Reads**: the user plays with dozens of mods. A page that reads characters, leaders, states or equipment is also checked with one such mod loaded beside this one, and the report says which mods a check had loaded. Generals a mod adds by event were missing from the Officers list in every check made with this mod alone (X66). The steps for that, and for letting time run, are in `wiki/Game-Recipes.md`.
- **The User's Playset Is Checked Too**: `python -I tools/check_playset.py` reads the launcher's active playset and reports, without the game, where its mods meet this one: windows both define, sprites a mod drops or resizes, hotkeys, scripted GUIs on the same tabs, and the content the pages name. `tools/Invoke-GameSteps.ps1 -Start -Playset -AfterLoad tools/playsets/<name>.json` starts the game with that playset, this mod last. Run both when a page or a screen is new and when the playset changes; `wiki/Compatibility.md` has the method and what each checkpoint found. A text another mod can make longer (a name, a label) gets a box of a fixed size (W28). In `error.log`, read also the lines that do not name the mod: "Could not find sprite type" and "invalid scope for var" name no file.
- **Recipes Bring A Screen Up**: each scene's `setup` is a recipe, a short list of steps from the clean state (paused 1936 Germany, all divisions in Army 1, nothing open, Home camera) to the screen: a hotkey (`{"key":"u"}`), a click on a widget by name (`{"clickWidget":"army_division_view/unitinfo_button"}`, aimed by the renderer, so it survives layout changes), a shared move from `tools/moves.json` (`{"move":"select_army_1"}`), or a raw position for the map. The scene's `expect` widgets are searched in the capture, which proves the screen came up. Every roadmap screen already has a recipe and a vanilla reference; `wiki/Game-Recipes.md` lists them and gives the method for a new one (`tools/Invoke-GameSteps.ps1` runs single steps in an open game and saves grid captures to read positions from). When a rework moves or replaces something a raw step clicks, turn that step into a `clickWidget`.
- **Reference Captures**: `reference/vanilla/` holds every roadmap screen as the game shows it without the mod, `reference/mod/` the reworked screens as the mod last left them: `<screen>.jpg` is the whole frame (context, and what `render_gui.py --over` draws on), `<screen>-panel.png` the panel at 1:1 without loss (read and measure here). Look there before asking for a screenshot or starting the game; `reference/README.md` is the index. Refresh with `-SaveReference` when a phase closes or the game updates.
- **Keep Image Encoding Out Of The Harness**: `tools/GameHarness.ps1` simulates input and copies the screen to PNG, nothing more. Windows Defender deleted it once, as `HackTool:PowerShell/EmpireGetScreenshot`, when JPEG encoding was added beside the screen copy. Image conversion belongs in the Python tools (`tools/save_reference.py`). If the antivirus flags a tool, tell the user and restructure the code; do not disguise it, add exclusions or restore from quarantine yourself.
- **Ask The Human Only For What A Crop Cannot Settle**: tooltips, click targets, states the save does not show, and the judgement whether a width is too much. Give one numbered checklist per launch (the scene's `checklist`), and log every launch in `wiki/phases/<screen>.md`.
- **Record What A Launch Teaches**: a new engine behaviour goes into the knowledge register (section 6) with its status and evidence, and the prose rule into `wiki/Design-Rules.md`. Give the record the alias of its section on `wiki/Engine-Facts.md` (`-Alias 1440p:W31`, the next free number) or on `wiki/Script-Reference.md` (`-Alias 1440p-script:L19`), then export, so that it shows on that page.

## 4. Build & Automation Protocol
- Before a game check, and before declaring work complete, run `powershell -File .\build.ps1 -Check <screen>`: validation, the whole Pester suite and the scene render in one go (add `-InGame` to finish with the unattended game check). The pieces are `build.ps1 -ValidateOnly`, `build.ps1 -Test` and `tools/render_gui.py`.
- Keep `.ps1` files pure ASCII. Windows PowerShell 5.1 reads a script without BOM as ANSI, so any other character is garbled or breaks parsing. Python tools run with `python -I` and need Pillow.
- Use `.\build.ps1 -DevLink` for zero-copy live editing directly from the repository; the harness needs it.
- Use `.\build.ps1 -Package` to verify that release packaging strictly excludes `.git`, `.github`, `.vscode`, `tests`, `wiki`, `tools`, `baseline`, `reference`, `scratch` and developer scripts.

## 5. Git & Commit Guidelines
- Do not commit to the Git repository unless explicitly instructed by the user. The user prefers to review changes before committing.
- **Git Verification Invariant**: After completing changes, always verify `git status` to ensure the working tree reflects expected changes.

## 6. Engine Knowledge
- Facts about how the game and its engine behave live in one place: the knowledge register of the Modding Manager, reached through the user-level `hoi4-modding-knowledge` skill. Search it before writing a kind of mod file for the first time in a session and before asking for a game launch.
- Do not write an engine fact into this repository (this file, `wiki/`, skills, tool comments). Add it to the register with `Add-HoiKnowledge.ps1` and cite its id. This mod's docs and tools cite the ids of `wiki/Engine-Facts.md` (W14, X23) and `wiki/Script-Reference.md`; those pages are generated from the register by `Export-HoiKnowledge.ps1 -Repo hoi4-1440p-ui-mod`, and the ids are the records' aliases, so both forms resolve (`Find-HoiKnowledge.ps1 -Id W14`). Newer facts are cited by register id, as in `[LOAD-012]`.
- Topics this mod leans on: `gui-widgets`, `gui-layout`, `gui-sprites-and-fonts`, `scripted-gui`, `script-language`, `localisation`, `loading-and-overrides`, `game-automation`, `engine-limits`.
- The interface skill is the user-level `hoi4-gui-modding`, shared with the author's other mods; this repository keeps no copy of it.
- `tests/Knowledge.Tests.ps1` runs the register's audit for this repository. Keep it identical to the Manager's `Scripts/Knowledge/Knowledge.Tests.ps1`.
