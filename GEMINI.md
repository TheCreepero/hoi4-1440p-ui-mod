# HOI4 1440p UI Mod - Development & Agent Rules

## 1. Mod Architecture & Workspace Layout
- **Mod Role**: High-resolution UI mod that redesigns Hearts of Iron IV screens for 1440p (`2560x1440`) and higher displays: larger and regrouped panels, a place of its own for every value a screen already has, larger text, and hotkeys for existing buttons.
- **Checksum Invariant**: Mod content lives only in `interface/` (`.gui`, `.gfx`) and `gfx/` (textures). Neither is part of the gameplay checksum, which keeps the mod 100% compatible with Ironman, achievements, and multiplayer. `common/`, `events/`, `history/` and `map/` stay empty. **Planned exception (user decision, 2026-10-12):** scripted GUIs under `common/scripted_guis/` may become part of this mod in phase D2 of `wiki/Roadmap.md`, at the cost of Ironman and achievement compatibility. Until that phase adds the first one, nothing goes under `common/`; that phase also changes this rule, its tests, the README and the Workshop text.
- **Phased Work**: The mod is built one screen per phase. Before starting or continuing a phase, read `wiki/Roadmap.md` (phase list, status), `wiki/Design-Rules.md` (the rules and the per-screen recipe), `wiki/Engine-Facts.md` (what is confirmed, provisional or untested about the engine) and the phase's notes in `wiki/phases/` (template: `wiki/Phase-Template.md`).
- This project follows a unified single-root mod layout:
  - **Workspace & Git root**: `C:\dev\hoi4-1440p-ui-mod` (Git repository root containing `.git/`)
  - All mod descriptors (`descriptor.mod`), build tools (`build.ps1`), interface definitions (`interface/`), content (`common/`), tests (`tests/`), and agent configurations (`GEMINI.md`) reside at the project root.
  - `tools/` (inspection, render and harness scripts), `baseline/` (vanilla reference copies of overridden windows), `reference/` (captures of every screen, vanilla and reworked) and `scratch/` (renders, captures, caches; git-ignored) are dev-only and excluded from packages.

## 2. Clausewitz GUI & File Format Invariants
- **UTF-8 Without BOM**: All Clausewitz script and interface files (`.mod`, `.txt`, `.gui`, `.gfx`) must be saved in UTF-8 without BOM. Never use standard Windows PowerShell `Set-Content -Encoding UTF8` because it writes a BOM (`\ufeff`). Always write text files using:
  `[System.IO.File]::WriteAllText($path, $content, [System.Text.UTF8Encoding]::new($false))`
- **Hardcoded C++ Widget Bindings**: The Clausewitz engine binds gameplay data exclusively to predefined widget `name = "..."` attributes. Never rename vanilla element names inside overridden windows, and keep each named widget under its vanilla parent.
- **No New Data Or Actions**: The engine fills only the widgets its code asks for, so a redesign can re-arrange, enlarge, caption and add hotkeys, but cannot add live values or working buttons. Before proposing an addition, run `tools/Show-CodeNames.ps1 <file.gui> <window>` and read "What a redesign can add" in `wiki/Design-Rules.md`. Scripted GUIs can add both, for values of the country, but live in `common/` and change the checksum: they are allowed only in the phases the roadmap plans them for (Milestone D).
- **One Override File Per Screen**: Put a screen's reworked top-level windows in `interface/zz_1440p_<screen>.gui` and leave the vanilla file alone. The game uses the last loaded definition of a window name and loads `.gui` files in name order, so the `zz_` prefix is what makes the override win.
- **Baseline Before Rework**: Start or extend a screen file with `tools/New-OverrideFile.ps1 <screen> <file.gui> <window> [<window> ...]`. It saves each window's vanilla text under `baseline/`, writes untouched copies into `interface/zz_1440p_<screen>.gui` and creates `tools/scenes/<screen>.json`. The test suite fails for an overridden window without a baseline, and for any named vanilla widget that is missing or moved.
- **Links Live In Code**: Which rows fill a list or grid, and which file-level `@variables` a window needs, is known only to the game code. Record each in `tools/gui-links.json`; the tests, the renderer and the harness read it.
- **Review Against The Baseline**: After editing, run `tools/Compare-Baseline.ps1 zz_1440p_<screen>.gui` (`-Group` for one line per widget) and read every changed value. Nothing but intended changes may appear.
- **Sprite Naming**: Name new sprites `GFX_1440p_*` and declare them in `interface/1440p_ui.gfx`. Leave vanilla sprite names untouched.
- **Art From Vanilla Assets**: Build every image from vanilla game assets, following the order of options in `wiki/Design-Rules.md`. AI-generated images are not allowed anywhere in the mod.
- **Key-Value Syntax**: `descriptor.mod` must strictly follow `key="value"` without spaces around the `=` operator.
- **Bracket Balance**: Curly braces `{}` and double quotes `""` must always be strictly balanced.
- **Usable Slot Width & Scroll Math**: In scrollable windows with `verticalScrollbar = "right_vertical_slider"`, match `slotsize.width` to the entry `containerWindowType.width`, and set `scroll_wheel_factor` to an integer multiple of `slotsize.height`.
- **Vanilla Lookups**: Inspect vanilla `.gui` structure with `tools/Show-GuiOutline.ps1 <file.gui> [<window>] [-All|-Comments]` instead of guessing (`-Comments` lists the sizes "set in code"). For `.gui`/`.gfx` syntax and element templates, read `.agents/skills/hoi4-gui-modding/SKILL.md`. For other vanilla facts, use the user-level `hoi4-vanilla-lookup` skill.

## 3. Seeing The Result
- **Render Before Asking**: `python -I tools/render_gui.py --scene <screen>` draws the screen from the override file with the real textures and fonts into `scratch/previews/` (`--over` composes it on the vanilla screenshot, `--bounds` outlines every widget, `--expand <dropdown>` opens one). Read the crop PNG with the Read tool. No game check is requested before the render has been looked at and the problems it shows are fixed. The scene file `tools/scenes/<screen>.json` holds the window positions, sample texts, rows per list and the widgets the code hides; keep it current.
- **Check In The Game Yourself**: the game re-reads no `.gui`, `.gfx` or texture file while it runs (`reloadinterface`, `reload <file>` and `reload_textures` report success and change nothing; `wiki/Engine-Facts.md` H3, H4), so every change is checked from a fresh start. `tools/Invoke-GameCheck.ps1 <screen> [<screen> ...]` does the whole round without a human in about two minutes: only-this-mod playset, `hoi4.exe -debug`, the menu clicks into a new 1936 game as Germany (paused, never saved), the scene's `setup` steps that bring the screen up, a capture and a 2x crop per scene into `scratch/checks/`, the `error.log` diff against `baseline/error.log.vanilla`, then it stops the game and restores the playset. Read the crops with the Read tool. `-Vanilla` captures the same screens without the mod, `-SaveReference` stores the captures for good under `reference/`, `-KeepRunning` leaves the game open for the user, `-NoRestart` reuses a running game. It takes over the main screen and the mouse while it runs, so ask the user for permission before starting the game, each time, saying what the launch is for, and batch changes: render first, launch when the render looks right.
- **Recipes Bring A Screen Up**: each scene's `setup` is a recipe, a short list of steps from the clean state (paused 1936 Germany, all divisions in Army 1, nothing open, Home camera) to the screen: a hotkey (`{"key":"u"}`), a click on a widget by name (`{"clickWidget":"army_division_view/unitinfo_button"}`, aimed by the renderer, so it survives layout changes), a shared move from `tools/moves.json` (`{"move":"select_army_1"}`), or a raw position for the map. The scene's `expect` widgets are searched in the capture, which proves the screen came up. Every roadmap screen already has a recipe and a vanilla reference; `wiki/Game-Recipes.md` lists them and gives the method for a new one (`tools/Invoke-GameSteps.ps1` runs single steps in an open game and saves grid captures to read positions from). When a rework moves or replaces something a raw step clicks, turn that step into a `clickWidget`.
- **Reference Captures**: `reference/vanilla/` holds every roadmap screen as the game shows it without the mod, `reference/mod/` the reworked screens as the mod last left them: `<screen>.jpg` is the whole frame (context, and what `render_gui.py --over` draws on), `<screen>-panel.png` the panel at 1:1 without loss (read and measure here). Look there before asking for a screenshot or starting the game; `reference/README.md` is the index. Refresh with `-SaveReference` when a phase closes or the game updates.
- **Keep Image Encoding Out Of The Harness**: `tools/GameHarness.ps1` simulates input and copies the screen to PNG, nothing more. Windows Defender deleted it once, as `HackTool:PowerShell/EmpireGetScreenshot`, when JPEG encoding was added beside the screen copy. Image conversion belongs in the Python tools (`tools/save_reference.py`). If the antivirus flags a tool, tell the user and restructure the code; do not disguise it, add exclusions or restore from quarantine yourself.
- **Ask The Human Only For What A Crop Cannot Settle**: tooltips, click targets, states the save does not show, and the judgement whether a width is too much. Give one numbered checklist per launch (the scene's `checklist`), and log every launch in `wiki/phases/<screen>.md`.
- **Record What A Launch Teaches**: a new engine behaviour goes into `wiki/Engine-Facts.md` with its status and evidence, and the prose rule into `wiki/Design-Rules.md`.

## 4. Build & Automation Protocol
- Before a game check, and before declaring work complete, run `powershell -File .\build.ps1 -Check <screen>`: validation, the whole Pester suite and the scene render in one go (add `-InGame` to finish with the unattended game check). The pieces are `build.ps1 -ValidateOnly`, `build.ps1 -Test` and `tools/render_gui.py`.
- Keep `.ps1` files pure ASCII. Windows PowerShell 5.1 reads a script without BOM as ANSI, so any other character is garbled or breaks parsing. Python tools run with `python -I` and need Pillow.
- Use `.\build.ps1 -DevLink` for zero-copy live editing directly from the repository; the harness needs it.
- Use `.\build.ps1 -Package` to verify that release packaging strictly excludes `.git`, `.github`, `.vscode`, `tests`, `wiki`, `tools`, `baseline`, `reference`, `scratch` and developer scripts.

## 5. Git & Commit Guidelines
- Do not commit to the Git repository unless explicitly instructed by the user. The user prefers to review changes before committing.
- **Git Verification Invariant**: After completing changes, always verify `git status` to ensure the working tree reflects expected changes.
