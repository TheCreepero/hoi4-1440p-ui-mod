# Working Rules

The detailed working rules of the agents on this mod: the GUI and file invariants, how a result is seen and checked, and the roles of a phase. The scripted GUI rules went with the pages to the mod HOI4 Manager Pages (`../hoi4-manager-pages`) on 2026-10-21. `AGENTS.md` holds the short form and says when to read which section; the `/phase` skill reads this page at the start of a phase.

Moved here from `GEMINI.md` on 2026-10-18, when the rule file was reduced to the rules that always apply; `AGENTS.md` says when to read which section.

## 1. Phased Work
- **Phased Work**: The mod is built one screen per phase. Before starting or continuing a phase, read `wiki/Roadmap.md` (phase list, status), `wiki/Workflow.md` (who does each step, the handoffs and the user's gates; section 7), `wiki/Design-Rules.md` (the rules and the per-screen recipe), `wiki/Engine-Facts.md` (what is confirmed, provisional or untested about the engine) and the phase's notes in `wiki/phases/` (template: `wiki/Phase-Template.md`).

## 2. Clausewitz GUI & File Format Invariants
- **UTF-8 Without BOM**: All Clausewitz script and interface files (`.mod`, `.txt`, `.gui`, `.gfx`) must be saved in UTF-8 without BOM. Never use standard Windows PowerShell `Set-Content -Encoding UTF8` because it writes a BOM (`\ufeff`). Always write text files using:
  `[System.IO.File]::WriteAllText($path, $content, [System.Text.UTF8Encoding]::new($false))`
- **Hardcoded C++ Widget Bindings**: The engine binds gameplay data to widgets by `name = "..."`. Never rename a vanilla widget or change its element type inside an overridden window. A vanilla widget may move into a container of the mod's own, named `mod1440_*`, because `hoi4.exe` on this machine is patched to search nested containers (`wiki/Engine-Facts.md` W34); scrollbars, list boxes and browsers stay under their vanilla parent. After a game update run the Modding Manager's `Scripts\Executable\Set-HoiRecursiveLookups.ps1 -Status` and patch again before a game check, or wrapped widgets stay empty.
- **No New Data Or Actions**: The engine fills only the widgets its code asks for, so a redesign can re-arrange, enlarge, caption and add hotkeys, but cannot add live values or working buttons. Before proposing an addition, look the window up in the Modding Manager's `Artifacts/executable/window-bindings-1440p*.md` and read "What a redesign can add" in `wiki/Design-Rules.md`. Scripted GUIs can add both, for values of the own country: since 2026-10-21 they are the mod HOI4 Manager Pages (`../hoi4-manager-pages`), never this one.
- **One Override File Per Screen**: Put a screen's reworked top-level windows in `interface/zz_1440p_<screen>.gui` and leave the vanilla file alone. The game uses the last loaded definition of a window name and loads `.gui` files in name order, so the `zz_` prefix is what makes the override win.
- **Baseline Before Rework**: Start or extend a screen file with `tools/New-OverrideFile.ps1 <screen> <file.gui> <window> [<window> ...]`. It saves each window's vanilla text under `baseline/`, writes untouched copies into `interface/zz_1440p_<screen>.gui` and creates `tools/scenes/<screen>.json`. The test suite fails for an overridden window without a baseline, and for any named vanilla widget that is missing or moved.
- **Links Live In Code**: Which rows fill a list or grid, and which file-level `@variables` a window needs, is known only to the game code. Record each in `tools/gui-links.json`; the tests, the renderer and the harness read it.
- **Review Against The Baseline**: After editing, run `tools/Compare-Baseline.ps1 zz_1440p_<screen>.gui` (`-Group` for one line per widget) and read every changed value. Nothing but intended changes may appear.
- **Sprite Naming**: Name new sprites `GFX_1440p_*` and declare them in `interface/1440p_ui.gfx`. Leave vanilla sprite names untouched, with one exception: a sprite the code puts on a widget by its vanilla name, shown only by the reworked screen, may be declared again with a wider texture in `interface/zz_1440p_vanilla_sprites.gfx` [LOAD-012] (user, 2026-10-16). Add its name to the list in `tests/GuiInvariants.Tests.ps1`.
- **Art From Vanilla Assets**: Build every image from vanilla game assets, following the order of options in `wiki/Design-Rules.md`. AI-generated images are not allowed anywhere in the mod.
- **Key-Value Syntax**: `descriptor.mod` must strictly follow `key="value"` without spaces around the `=` operator.
- **Bracket Balance**: Curly braces `{}` and double quotes `""` must always be strictly balanced.
- **Usable Slot Width & Scroll Math**: In scrollable windows with `verticalScrollbar = "right_vertical_slider"`, match `slotsize.width` to the entry `containerWindowType.width`, and set `scroll_wheel_factor` to an integer multiple of `slotsize.height`.
- **Vanilla Lookups**: Inspect vanilla `.gui` structure with `tools/Show-GuiOutline.ps1 <file.gui> [<window>] [-All|-Comments]` instead of guessing (`-Comments` lists the sizes "set in code"). For `.gui`/`.gfx` syntax and element templates, use the user-level `hoi4-gui-modding` skill. For other vanilla facts, use the user-level `hoi4-vanilla-lookup` skill.
- **Reading The Executable**: the Modding Manager keeps a Ghidra project of `hoi4.exe` and the tools around it in its `Scripts\Executable` folder, whose `README.md` is the runbook. When a question is what the code fills, sets or binds, read it there before promising a layout or asking for a game check; the open questions are Milestone F in `wiki/Roadmap.md`. Never change `hoi4.exe` on your own: a patch is the user's decision, goes through the Manager's scripts so its hashes are recorded, and makes the mod local-only (`wiki/Roadmap.md`, Decisions). The installed executable carries the division icon picker patch [LIM-003]. It changes only that picker, which this mod does not touch, so game checks still show this mod as the unpatched game shows it.

## 3. Seeing The Result
- **Design Page Before Building**: a new screen or a larger change starts as a design page the user reviews: vanilla captures beside mock-ups at the same scale (`tools/mockup.py`, drawn from the phase's `layout.json`), what changes, what is open; `python -I tools/make_design_page.py <id>` makes the page from the handoff files. Build only what the user agreed on, then add the renders of the build to the page. The method is step 2 of the recipe in `wiki/Design-Rules.md`.
- **One Layout File**: the numbers of a proposal live in `scratch/phases/<id>/layout.json` (`wiki/Workflow.md`, "Handoff files"; the pieces in `wiki/Design-Language.md`). `tools/mockup.py` draws the mock-up from it and `tools/apply_layout.py` lays out the override file from it, so the two cannot drift; `apply_layout.py --compare <file>` is read at gate B. A designer reads the Manager's bindings reports by window (`window-bindings-all.md` has every window of the game) and never the decompiled code inside a phase; a window the reports miss is a question for the orchestrator, who regenerates them.
- **Render Before Asking**: `python -I tools/render_gui.py --scene <screen>` draws the screen from the override file with the real textures and fonts into `scratch/previews/` (`--over` composes it on the vanilla screenshot, `--bounds` outlines every widget, `--expand <dropdown>` opens one). Read the crop PNG with the Read tool. No game check is requested before the render has been looked at and the problems it shows are fixed. The scene file `tools/scenes/<screen>.json` holds the window positions, sample texts, rows per list and the widgets the code hides; keep it current.
- **Check In The Game Yourself**: the game re-reads no `.gui`, `.gfx` or texture file while it runs (`reloadinterface`, `reload <file>` and `reload_textures` report success and change nothing; `wiki/Engine-Facts.md` H3, H4), so every change is checked from a fresh start. `tools/Invoke-GameCheck.ps1 <screen> [<screen> ...]` does the whole round without a human in about two minutes: only-this-mod playset, `hoi4.exe -debug`, the menu clicks into a new 1936 game as Germany (paused, never saved), the scene's `setup` steps that bring the screen up, a capture and a 2x crop per scene into `scratch/checks/`, the `error.log` diff against `baseline/error.log.vanilla`, then it stops the game and restores the playset. Read the crops with the Read tool. `-Vanilla` captures the same screens without the mod, `-SaveReference` stores the captures for good under `reference/`, `-KeepRunning` leaves the game open for the user, `-NoRestart` reuses a running game. It takes over the main screen and the mouse while it runs, so ask the user for permission before starting the game, each time, saying what the launch is for, and batch changes: render first, launch when the render looks right. In a phase the orchestrator asks, once, naming the scenes and the number of launches, and only the game checker launches (section 7); a vague grant is not a grant.
- **Ten Days At Most, Never Save**: a check saves nothing, and stays paused on 1 January 1936 unless time is what it checks. The user's autosave is monthly: a check that let a month pass would overwrite the autosave of their own campaign. Since 2026-10-12 the user allows a check to run up to ten days inside January 1936, with a copy of `autosave.hoi4` made first and its hash compared afterwards (`wiki/Scripted-GUIs.md`, "Working on a page"; nine days left the file untouched, `wiki/Engine-Facts.md` X54). Read the clock from a capture after every burst. What needs more time than that, or a save, is asked of the user.
- **The User's Playset Is Checked Too**: `python -I tools/check_playset.py` reads the launcher's active playset and reports, without the game, where its mods meet this one: windows both define, sprites a mod drops or resizes, hotkeys. `tools/Invoke-GameSteps.ps1 -Start -Playset -AfterLoad tools/playsets/<name>.json` starts the game with that playset, this mod last. Run both when a screen is new and when the playset changes; `wiki/Compatibility.md` has the method and what each checkpoint found. A text another mod can make longer (a name, a label) gets a box of a fixed size (W28). In `error.log`, read also the lines that do not name the mod: "Could not find sprite type" and "invalid scope for var" name no file.
- **Recipes Bring A Screen Up**: each scene's `setup` is a recipe, a short list of steps from the clean state (paused 1936 Germany, all divisions in Army 1, nothing open, Home camera) to the screen: a hotkey (`{"key":"u"}`), a click on a widget by name (`{"clickWidget":"army_division_view/unitinfo_button"}`, aimed by the renderer, so it survives layout changes), a shared move from `tools/moves.json` (`{"move":"select_army_1"}`), or a raw position for the map. The scene's `expect` widgets are searched in the capture, which proves the screen came up. Every roadmap screen already has a recipe and a vanilla reference; `wiki/Game-Recipes.md` lists them and gives the method for a new one (`tools/Invoke-GameSteps.ps1` runs single steps in an open game and saves grid captures to read positions from). When a rework moves or replaces something a raw step clicks, turn that step into a `clickWidget`.
- **Reference Captures**: `reference/vanilla/` holds every roadmap screen as the game shows it without the mod, `reference/mod/` the reworked screens as the mod last left them: `<screen>.jpg` is the whole frame (context, and what `render_gui.py --over` draws on), `<screen>-panel.png` the panel at 1:1 without loss (read and measure here). Look there before asking for a screenshot or starting the game; `reference/README.md` is the index. Refresh with `-SaveReference` when a phase closes or the game updates.
- **Keep Image Encoding Out Of The Harness**: `tools/GameHarness.ps1` simulates input and copies the screen to PNG, nothing more. Windows Defender deleted it once, as `HackTool:PowerShell/EmpireGetScreenshot`, when JPEG encoding was added beside the screen copy. Image conversion belongs in the Python tools (`tools/save_reference.py`). If the antivirus flags a tool, tell the user and restructure the code; do not disguise it, add exclusions or restore from quarantine yourself.
- **Ask The Human Only For What A Crop Cannot Settle**: tooltips, click targets, states the save does not show, and the judgement whether a width is too much. Give one numbered checklist per launch (the scene's `checklist`), and log every launch in `wiki/phases/<screen>.md`.
- **Record What A Launch Teaches**: a new engine behaviour goes into the knowledge register (section 6) with its status and evidence, and the prose rule into `wiki/Design-Rules.md`. Give the record the alias of its section on `wiki/Engine-Facts.md` (`-Alias 1440p:W31`, the next free number) or on `wiki/Script-Reference.md` (`-Alias 1440p-script:L19`), then export, so that it shows on that page.

## 7. Workflow And Roles
- **One Phase, Four Roles** (user decision, 2026-10-16): a phase is run by an orchestrator (the interactive session) with three kinds of agent, and the user decides at three gates. `wiki/Workflow.md` is the page that assigns the recipe steps of `wiki/Design-Rules.md` to the roles and gives the handoff files; the roles are the agent definitions under `.claude/agents/`, the runbook is the skill `/phase <id> [<scene> ...]` (`.claude/skills/phase/SKILL.md`, mirrored byte for byte under `.agents/skills/phase/` for Antigravity; edit the Claude copy and copy it over, the knowledge audit and `tests/Workflow.Tests.ps1` check both). Invoking `/phase` is the user's standing request to spawn those agents.
- **Roles**: `designer` (Claude Opus 5.5) proposes, read-only on the repository; `builder-screen` (Claude Sonnet 5.5) builds a vanilla screen and `builder-script` (Claude Opus 5.5) a fix whose cause is unknown (it built the scripted pages until they moved to the mod HOI4 Manager Pages (`../hoi4-manager-pages`)); `game-checker` (Claude Opus 5.5) runs the harness and reads the captures, fixes nothing. The orchestrator reviews every handoff itself (the JSON, the composite image of every figure group, the layout compare, the baseline diff, the test output), reads the checker's evidence cuts and one overview capture per scene after the checker (user, 2026-10-20; before that every crop), makes and publishes the design page, and alone writes the knowledge register, `wiki/Roadmap.md`, `README.md` and `descriptor.mod`.
- **The User's Gates**: 1. the design page and its decisions, before anything is built; 2. the launches of the phase, granted once by name; 3. the final report, after which the user tests in their own game and commits. No agent starts the game or commits on its own.
- **Fix Rounds Continue The Same Builder**: findings of a check or of the user's own game go back to the builder that built the component, with the evidence cuts; the checker re-runs only the scenes a fix touched. The builder records each fix in `scratch/phases/<id>/fixes.json`, from which `tools/phase_notes.py` writes the notes.
- **Short Path For Small Phases** (user, 2026-10-20): a phase whose verdict would be `refine` at effort S (a card pass, a chip, a hotkey, a width, a caption) has no designer agent: the orchestrator writes `layout.json` and `design.json` itself with one figure group, makes the page and stops at gate 1 as always; builder and checker follow as in any phase (`wiki/Workflow.md`, "The short path").
- **Handoffs Live Under `scratch/phases/<id>/`** (git-ignored): `contracts.md`, `layout.json`, `design.json` and the mock-ups, `decisions-final.json`, `build/build.json` and the build renders, `checks/check-<n>.json` with its evidence cuts, `fixes.json`. The durable record is the phase notes (Proposal, Build, Game checks and Fix rounds generated from the handoffs by `python -I tools/phase_notes.py <id>` at every gate; Scope, Roles, Inventory, Decisions and Close by hand) and the published design page; the orchestrator keeps both current the day it happens.
